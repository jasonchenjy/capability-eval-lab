# Minimal versioned Verifier Contract — current revision 2

Approved architecture: v2, Phase 5A implementation only. The only new executable strategy is `black-box-json-v2`, contract version 2, threat model `frozen-api-inert-pattern-v1`. The legacy Phase 3 AST fixture remains separate. `repository-test-v1` is a reserved design direction, **not an accepted strategy**. No dynamic module/plugin loader exists.

The trusted caller supplies a suite, snapshot manifest, lock and external expected lock digest. The lock binds exact snapshot/suite hashes, mandatory count, adapter and implementation hashes, image ID, timeout and strategy. The implementation rejects any unsupported or changed field by exact comparison with its supported lock. It checks before and after execution. This is an integrity contract under a trusted operator, not a signature or defense against someone changing both implementation and approval root.

Private suite format: a list of unique IDs, `request` and `expected`. Request operation `splitlines` has string `text` and expects a string list; `indent` additionally has string `margin` and `newline` and expects a string. Both operations and at least two cases are required. The suite is bounded and provisioned privately, not embedded in source/tests. Candidate receives only a request. Public protocol response is `{version: 1, value: ...}` or `{version: 1, error: "candidate_exception"}`. The latter is an ordinary functional failure. stdout is untrusted, strictly parsed, bounded and never interpreted as a score.

The host driver holds expected outcomes; it never imports candidate code. Candidate processes run with no network/host mounts/credentials, nonroot, read-only root, bounded tmpfs, CPU/memory/PIDs/output/time, in the pinned Phase 3 image. Source is reconstructed from the immutable full public snapshot and admitted replacement. Python imports only inside the candidate container. One fresh container per verification; one fresh interpreter per test request. Requests in a run share the container, so state or background processes can persist within that run; no claim of request secrecy or per-case isolation is made. Trial state does not cross runs. Candidate receives public source/tests but no private assertion files or expected results. Controller-to-candidate stdin and bounded stdout are the entire test interface; no host control/result files are mounted.

Version 1 incorrectly treated protocol-correct stdout as evidence of API behavior. Review demonstrated a broken library could read the adapter request and fabricate correct responses. Version 2 therefore freezes every executable byte of the library except one inert regex string literal; arbitrary candidate Python is not accepted. A private finite suite does not prove universal correctness or prevent overfitting to all observed inputs. A narrow public-example overfit is a qualification negative control. Result provenance records hashes, not raw private inputs/outputs. Authoritative grading runs outside the candidate namespace. Candidate subprocess exit without a valid protocol, timeout, malformed output, excess output, incomplete suite, broken image/transport or changed trusted inputs are invalid/null. Valid responses that disagree with expected outputs or a caught candidate exception are fail/0. Pass/1 requires every declared check to complete and pass. No candidate score/report is accepted.

Repository Test Verifier, when separately authorized, needs its own threat model: colocated pytest/candidate execution cannot inherit the claim that assertion code is unreadable. It must qualify plugin/import/test-discovery manipulation, forged reports, missing tests and isolation explicitly. The black-box adapter is not a restriction imposed on all future evaluation tasks.


## Review correction: code admission and qualification authority

The edit policy `boltons-line-ending-literal-v1` permits only the single string literal passed to the baseline `_line_ending_re = re.compile(...)`. Prefix and suffix bytes must exactly equal the pinned source. A bounded tokenizer and constant-node check accept exactly one ordinary/raw string token; bytes, f-strings, calls, concatenations, comments and inserted statements are rejected. No candidate code executes on the host, no regex is evaluated on the host, and the Phase 3 AST evaluator is unchanged. Regex behavior is still tested through the actual frozen APIs in the sandbox. Malformed regexes fail functionally; catastrophic regexes hit the real timeout.

This is a deliberate **narrowing of accepted solutions**, not a general solution to authenticating arbitrary hostile Python in-process. A correct repair outside the literal is unsupported/invalid. The public task and scenario disclose the restriction. Both positive controls have different literal spellings (escaped versus literal Unicode), not different API algorithms. The suite, baseline and expected outcomes are unchanged; the contract/approval roots are new. General repository/API repairs still need a separately qualified strategy.

Qualification now requires an external expected scenario digest as well as the verifier digest. It binds snapshot/revision, public instruction, verifier strategy/lock and edit policy; requires the exact control inventory and every approved patch hash; loads control bytes once and executes those same bytes; rejects identical positive bytes and identical reconstructed positive trees. It rechecks the private suite and on-disk controls after execution. A changed scenario, instruction or control is rejected before any candidate execution, not treated as a passing qualification merely because its score matches. These roots assume a trusted operator; they are not cryptographic reviewer authentication.
